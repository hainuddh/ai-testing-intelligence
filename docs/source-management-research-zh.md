# 信源管理改进研究（方案草案）

研究日期：2026-10-17。研究时的代码基线：`dde1c67`，下文描述当时的问题和建议，不作为当前功能清单。研究未读取生产环境的信源运行数据，不能据此判断现有某个信源的实际质量。

实施说明（2026-10-18）：本研究提出的关注方向、自动发现与独立试运行、人工确认、贡献看板和暂停归档已完成核心实现，操作与当前边界见[信源工作台说明](source-management-zh.md)。下文保留研究时的判断与分期，不能把后续扩展视为已经实现。

建议采用“关注方向驱动、平台主动维护、依据实际内容评估”的管理方式。用户主要定义关心什么、查看贡献和处理少量例外；平台负责发现候选、验证地址、限额试运行和持续检查。先让现有信源可理解、可暂停、可恢复，再扩大自动发现。

## 1. 当前体验的问题

| 当前实现 | 使用上的影响 | 建议 |
| --- | --- | --- |
| 自动发现要求先输入网站主页，再在站内查找 RSS/Atom | 用户仍需自己寻找网站，“自动发现”容易被理解为全网探索 | 当前入口称“通过网址添加”；另建按关注方向发现的能力 |
| 手动创建信源后还要另建端点，按钮却叫“建立监听” | 保存成功不代表已经开始采集 | 合并为网址输入、内容预览、确认启用的一条流程；无法采集时明确提示 |
| 页面主要展示名称、说明、主题和人工可信等级 | 看不出是否运行、最近贡献如何、哪些需要处理 | 增加运行状态、最近成功、近30天贡献、样例和异常原因 |
| 信源主题按来源保存，作为分析上下文及补取全文的参考 | 容易误以为已设置全局关注方向，或会严格过滤该源文章 | 区分平台关注方向与信源内容主题 |
| 常见操作为编辑、删除；信源删除级联删除采集内容 | 不想继续监听时缺少保留历史的退出方式 | 以暂停、恢复、归档作为日常操作，永久删除放入高级操作 |
| 卡片列表没有搜索、筛选和分页，前端只取前200条 | 信源增加后难以定位，统计总数可能与卡片数量不一致 | 服务端筛选、分页和全量统计，提供需处理视图 |

依据：[信源页面](../apps/web/src/App.tsx)、[信源接口](../apps/api/app/routers/sources.py)、[数据模型](../apps/api/app/models.py)、[分析流程](../apps/api/app/analyzer.py)。现有主题编辑器已经支持草稿、撤销移除和保存确认，应继续复用。

## 2. 成熟产品可借鉴的做法

- Feedly把按主题找源、输入网址、精选信源包放在同一发现体系中，并区分原始来源与经过条件筛选的信息流。这支持把“找什么”和“从哪里来”分别管理。[Feedly官方说明](https://docs.feedly.com/article/768-follow-sources-in-feedly)
- Inoreader将查询保存为持续监测的信息流，匹配范围可覆盖自己的订阅或其公共索引。这说明用户可以只定义方向，让系统持续发现相关文章；本项目若采用类似方式，需要自行准备候选目录或接入搜索服务，不能假设已经具备同等索引能力。[Inoreader监测信息流](https://www.inoreader.com/features/monitoring-feeds)
- Inoreader支持过滤规则的启停、条件预览及过滤结果统计。适合借鉴的是“规则可以解释并验证”，让用户知道为什么内容被留下或隐藏。[Inoreader自动化说明](https://www.inoreader.com/blog/2026/01/save-time-with-automations.html)
- FreshRSS支持默认及单个信源刷新间隔，以及标准OPML导入导出。批量迁移与更新频率管理值得纳入后续能力；本文提出的自适应调频是本项目建议，并非对该产品现有算法的描述。[刷新设置](https://freshrss.github.io/FreshRSS/en/users/09_refreshing_feeds.html)、[OPML说明](https://freshrss.github.io/FreshRSS/en/developers/OPML.html)

以上是交互与产品机制的参考，不代表这些机制已经在本项目验证效果，也不采用供应商宣传的效果倍率作为收益承诺。

## 3. 推荐的用户流程

### 关注方向

用户设置想持续了解的内容，例如AI辅助测试、Agent评测、接口自动化；可选语言、排除方向和信息量偏好。每个方向支持常用别名，减少AI testing、AI测试等同义写法造成的碎片。

单个信源保留“内容主题”，描述它通常发布什么；平台“关注方向”描述用户需要什么。两者可以多对多关联。GitHub可以选择复用同一个主题词库，但保留独立启停和搜索策略，不自动覆盖现有偏好。

### 添加与发现

保留三个入口：通过网址添加、从信源包选择、平台推荐。普通用户只需输入网址并查看实际文章样例，名称和语言尽量自动建议；RSS地址、采集间隔和条目上限放在高级设置。

平台推荐优先利用经过整理的信源目录及已采集文章中的真实来源链接，再考虑接入外部搜索。每个候选展示发现出处、匹配方向、3—5篇实际文章和可补充的内容覆盖。地址必须经过实际验证，不由模型凭空生成。

同一个规范化订阅地址不重复加入；同域名下不同栏目不直接当成同一信源。用户忽略或归档的候选记住处理决定，避免每轮重复推荐；重新纳入需有明确恢复行为或新证据提示。

### 试运行与正式使用

推荐流程：候选 → 试运行 → 正式监听；也可延长观察、暂停或归档。采集健康另作独立维度，一个正式信源也可能暂时异常。

平台按预先设置的策略自动发现和限额试运行，避免要求用户每天手动启动。观察期结合发布频率和样本量决定，不能把固定7天当成普遍适用的标准。初期给出保留、继续观察或暂停建议；“自动转为正式”作为一次性管理策略设置，默认保留人工确认。

试运行有独立请求量、文章量和模型调用预算。试运行内容可在预览中查看，默认不直接进入正式邮件，也不能成为每日邮件必须等待的任务。采集状态与交付资格需要分别控制。

## 4. 页面应该帮助用户做什么

建议保留一个信源管理入口，通过视图切换展示“正在监听、发现与试运行、需处理、已归档”。关注方向放在页面上方的独立设置入口。

默认用便于比较的列表，移动端保持紧凑卡片。展示信源、所属方向、采集状态、最近成功、近30天已分析/入选数量及操作。支持按名称或域名搜索，按方向、语言、状态筛选；不把所有高级配置堆进主列表。

点击信源打开详情：先展示代表内容和最近贡献，再提供采集设置与运行记录。未配置、正常但暂无新内容、部分端点异常、全部异常应明确区分。人工录入型来源显示自己的工作方式，不因没有自动端点就被判为故障。

常用操作为查看内容、暂停、恢复和编辑；归档保留内容、去重记录和运行历史。永久删除仍需明确说明影响。异常集中到“需处理”，显示可理解的原因和可执行的修复动作。

示例展示（仅为虚构数据，不是生产统计）：某测试博客，近30天已分析32篇、入选8篇，另有6篇待分析；最近成功采集2小时前。比“可信等级4、已采集38条”更能支持判断。

## 5. 怎样评价才更科学

先分开呈现三类证据：来源可信程度、与关注方向的匹配、采集运行情况。人工信誉不能替代事实核实，模型的测试价值分也不能证明来源可信。

| 观察维度 | 推荐口径 | 当前数据条件 |
| --- | --- | --- |
| 采集健康 | 最近成功、连续失败、成功次数/已完成尝试次数、失败分类 | 已有FetchRun，可聚合；需先纠正空订阅的误判 |
| 内容匹配 | 近30天采集且已完成分析的去重文章中，入选雷达数量/已分析数量 | 可以做基础统计，须展示样本数和待分析数 |
| 新增贡献 | 同一窗口新增入库与入选的数量，附代表文章 | 可以统计当前保留且归属于该源的样本，不能直接称为独家贡献 |
| 及时性 | 有可靠发布时间的内容，从发布到首次采集的延迟 | 只能对时间有效的样本计算，并显示字段覆盖率 |
| 重复与补充价值 | 每个源实际遇见的内容、与其他源重合情况、提供的新信息 | 缺少遇见记录与多来源归属，需先补采集 |
| 用户认可 | 有用、无关、已采用等明确反馈 | 需要新增事件；未点击或未反馈不能算无用 |
| 运行成本 | 每源请求次数、实际分析调用和token消耗 | 现有分析尝试次数不足以准确估算费用 |

统计窗口要一致；待分析、分析失败单列，不能把模型积压视为信源内容差。重分析、删除和分析规则变更会影响当前数据口径，应说明覆盖范围；长期对比需保留规则版本与事件记录。

小样本显示“观察中”，同时呈现分子和分母。不能把1/1判得比30/50更可靠。低频的官方公告、研究论文可以延长窗口；正常采集但没有新增并不等于故障或没有价值。

初期不设计单一百分制质量总分，也不按分数自动淘汰。若以后需要排序，应在相近类型与方向内比较，并考虑样本不确定性。对有独特覆盖的低频来源保留空间，避免高产量、热门来源占据全部位置。

还需避免评分自我强化：目前信源主题和人工可信等级已经进入文章分析上下文，不能再单凭这些文章的模型评分反推信源的客观可信度。应结合原文、来源证据和用户反馈。

## 6. 自动维护的边界

建议逐步加入：连续访问失败后的退避与重试、真实地址修复的可见记录、根据实际更新节奏提出调频建议，以及主题覆盖不足提示。用户可固定频率或保留某个信源。

低匹配先提示调整方向或暂停；不会自动删除历史。频率调整要同时关注内容遗漏和成本，不能只降低请求次数。定期回看被过滤的样例，才能发现规则是否漏掉有用内容。

以下现有行为需要在开发前处理：

1. 调度目前不检查Source.status；每日批次的必采端点还可能覆盖enabled=false。暂停需要定义即时生效边界，协调已排队、运行中和已冻结任务，不能只改页面标签。推荐暂停后停止新任务，对未执行的当日任务记录明确排除原因；正在执行的请求收尾，已冻结邮件保留原快照，界面解释当日影响。
2. 信源层health_status没有随端点采集统一汇总。应从有效端点与最近运行推导状态，不能直接把现有字段当真实健康结论。
3. 当前有效但没有条目的RSS可能进入“未发现有效订阅”失败路径。需先区分格式有效但暂无内容与解析/连接失败，避免错误扣分。
4. 网页端点对相同URL会重新进入分析，即使内容可能没变。先补正文变化判断与必要的条件请求，再优化调频和分析成本。
5. 当前跨源去重直接跳过其他来源，且文章只有一个source_id。新增量受采集先后影响；未补齐观测记录前，不展示准确重复率、原创率或独家贡献率。
6. 试运行必须与正式每日准备、邮件候选资格隔离，不能只增加一个trial标签。

依据：[调度](../apps/api/app/worker.py)、[每日批次](../apps/api/app/digest_batches.py)、[采集及修复](../apps/api/app/fetcher.py)、[去重](../apps/api/app/content_deduplication.py)。

## 7. 建议分三期落地

| 阶段 | 核心范围 | 完成后用户能得到什么 |
| --- | --- | --- |
| 第一期：可理解、可维护 | 统一网址添加；搜索筛选分页；真实运行状态与最近结果；端点编辑；暂停恢复、归档；基础贡献计数 | 知道哪些真正工作，方便找到问题，停用不丢历史 |
| 第二期：可评估、可探索 | 全局关注方向；补采集观测与反馈；信源包；平台候选发现；独立试运行；样例与推荐理由 | 不必自己找所有网站，可以根据证据决定是否长期使用 |
| 第三期：低维护成本 | 可解释的调频、失败退避、修复审计、覆盖缺口提醒；OPML导入导出 | 平台持续维护，用户主要处理例外和调整方向 |

第一期不必等待全网搜索接入，也不需要先开发复杂评分。第二期的外部搜索来源、资源预算和试运行规则需在具体设计中确定；现阶段不能承诺完全自动发现的覆盖范围。

验收不仅看页面完成，还应验证：添加后能清楚看到是否开始采集；暂停真实影响调度且不阻塞当日交付；归档保留历史与去重；低频来源不会被误判；指标显示样本及积压；试运行噪声不进入正式邮件；超出200个信源仍能查全。

产品效果可用添加成功率、添加所需操作数、发现异常与恢复的时间、每周人工维护次数衡量；同时跟踪经用户确认的有用内容和抽样漏检情况，防止单纯减少内容量带来虚假的质量提升。需先记录基线，再设提升目标。
