# GitHub 自动发现候选方案优化计划书

> 研究命题：GitHub 追踪能否做到「系统自动发现候选、无需用户手动新增数据源」？成本如何？
> 方法：三个独立视角（技术可行性 / 成本规模 / 产品体验）分别产出计划书，交叉比对矛盾点、多轮验证直至收敛，最终汇总为本计划书。

## 一、已核实的事实基础（三视角共同依赖）

| 事实 | 数据 | 来源 |
|---|---|---|
| Core API 限额（未认证） | **60 req/h** | GitHub 官方文档 |
| Core API 限额（PAT 认证） | **5000 req/h** | GitHub 官方文档 |
| Search API 限额（未认证） | **10 req/min（独立桶）** | GitHub 官方文档 |
| Search API 限额（认证） | **30 req/min（独立桶）** | GitHub 官方文档 |
| Search 查询约束 | ≤256 字符、≤5 个布尔操作符、每搜索最多 1000 结果（scope 4000）、per_page≤100 | GitHub 官方文档 |
| 二级限流 | 100 并发、900 points/min、90s CPU/60s；持续超限可能被**封禁集成** | GitHub 官方文档 |
| 自动发现信号实现 | `created:>日期 stars:>=N`（新创建高星）、日均星数+年龄平滑（加速度）、topic 聚合打分 | github-discover-cli 等成熟项目 |
| GitHub Trending 页面 | **无官方 API**，需 HTML 爬取 | 多项目共识 |

**关键结论**：Search API 与 Core API 是**两个独立配额桶**——「自动发现」走 Search（未认证 10/min 也够），「持续快照追踪」走 Core（未认证 60/h 是硬瓶颈）。这决定了「发现」与「追踪」必须分开评估。

## 二、三份独立计划书核心结论

### 计划书 A — 技术可行性

**结论：能做到，且已有成熟参考实现，技术风险低。**

1. 自动发现三种信号全基于 Search API 可实现：
   - `popular`：新创建 + 高星（出生即巅峰）
   - `trending`：日均星数（stars/day + 年龄平滑）找「加速度」
   - `topic`：热门仓库高频 topic 聚合打分
2. 分层架构清晰：`发现(Search) → 打分(确定性) → 快照(Core) → 分析(LLM) → 报告`。
3. **瓶颈**：无 token 下 Core API 60/h 限制快照规模——每日一次快照，追踪 200 repo 需排 3.3h，1000 repo 需 16.7h（接近不可行）。**规模化快照必须 token**。
4. 与现有系统同构，复用 `worker`（定时）+ `fetcher`（新增 Search 采集器）+ `analyzer`（LLM 分级）。

### 计划书 B — 成本规模

**结论：资金成本近零，真实成本是「配额 + LLM token + 注意力」。**

1. GitHub API：**0 资金成本**（无 token / fine-grained PAT 均免费）。真实约束是配额。
2. LLM 分析是本项目主要**可变成本**，随候选量线性增长 → 必须分级。
3. 存储：快照 ≈ repo 数 × 1 次/天 × 0.5KB，1000 repo 年约 200MB，可忽略。
4. 运维：rate limit 监控 + 封禁规避（持续超限可能被 ban）。
5. **最大隐性成本 = 噪声带来的用户注意力成本**——自动发现质量差，用户要花时间过滤，反而违背「减法定位」。

### 计划书 C — 产品体验

**结论：「无需用户新增」应解读为「零配置发现 + 轻量反馈」，而非「零参与」。**

1. 完全黑盒自动追踪 = 推荐一堆不相关项目，违背「省注意力」核心定位。
2. 自动发现的价值在**冷启动**——新用户进来即看到有价值的候选，无需手填 URL/搜索。
3. 正确设计：系统自动产出候选 → 确定性分层（高置信进观察、用户「关注」进追踪）→ 用户「关注/忽略」形成隐式偏好，持续校准。
4. 话术应从「无需新增数据源」改为「零配置发现，一键关注」，避免误导期待。

## 三、矛盾点交叉比对

| # | 矛盾点 | 各方立场 | 判定 |
|---|---|---|---|
| 1 | 无 token 是否够用 | A/B：发现够、追踪受限；C 未涉 | 分工而非冲突：发现可无 token，追踪规模化需 PAT |
| 2 | 全自动入库 vs 需确认 | 用户暗示全自动；C 反对黑盒；A 技术上可实现全自动但未考虑噪声；B 指噪声=隐性成本 | 收敛为「自动分层 + 轻量反馈」 |
| 3 | 每候选深度分析 vs 成本 | C 求质量→深度；B 求控成本→分级 | 收敛为「确定性打分先过滤 + 分级 LLM」 |
| 4 | 发现频率 vs 报告频率 | A 每日一跑；日报要「今日新星」但 created 过滤≠今日增量 | 区分「新项目发现」与「既有项目增量」两条独立调度 |

## 四、迭代验证（第二轮打回后修正）

- **A 修正矛盾 1**：核实 Search/Core 独立桶后，明确无 token 可支撑「发现（10/min）+ ≤200 repo 每日快照」，超过 200-500 repo 必须 PAT。
- **B 修正矛盾 2/3**：量化分级收益——每天 100 候选 → 确定性打分过滤 90% → 10 个高置信批量摘要（1 次 LLM）→ 3 个被关注深度分析（3 次）。token 从「100 次全量」降到「1+3 次」，**降约 90%**，分级必须纳入 MVP。
- **C 修正矛盾 2**：确认「零配置发现 + 一键关注」不违背用户诉求——用户仍无需手填 URL/搜索，只是对推荐做关注/忽略的轻量操作。

三个视角在此收敛，无不可调和矛盾。

## 五、最终优化计划书（汇总）

### 5.1 核心定位
「零配置自动发现 + 确定性分层 + 轻量反馈」，实现**用户无需手动新增数据源**，同时守住质量。

### 5.2 自动发现三层信号（基于 Search API，可无 token 起步）
1. `popular`：`created:>{24h/7d 前} stars:>=N`，按语言分组
2. `trending`：对候选算 `stars/day`（年龄平滑）排序
3. `topic`：候选 `topics` 字段聚合，按频次 + 总星数打分

### 5.3 分层处理流水线
```
发现(Search 每日) → 去重 → 确定性动量打分(免费) → [高置信]自动进观察列表
                                              → [用户关注]进追踪列表
分析(LLM 分级)：观察=不分析 / 高置信=批量轻量摘要 / 已追踪=深度分析(场景+组合+建议+风险)
报告：日报(快照 delta TopN) / 周报(趋势复盘) / 月报(组合分析+归档)
```

### 5.4 成本结论
- GitHub API：**0 资金成本**；无 token 支撑 MVP（发现 + ≤200 repo 追踪），规模化用免费 fine-grained PAT（5000/h）。**MVP 先无 token，Phase 3 再加 token**。
- LLM：分级后成本降 ~90%，是主要可控成本。
- 存储：可忽略。
- 注意力成本：用确定性打分 + 「忽略」反馈闭环控制。

### 5.5 技术落地对齐
完全复用现有 `worker` 定时 + `fetcher`（新增 Search 采集器）+ `analyzer`（分级）+ `ContentItem` 体系；新增 `GitHubRepo` + `GitHubSnapshot` 表 + 报告表。定稿后按 TDD 推进。

## 六、结论
「系统自动发现、无需用户手动新增数据源」**技术上可行、资金成本近零、与现有架构同构**。唯一需要修正认知的是：**「无需手动新增」不等于「无需任何参与」**——应以「零配置发现 + 一键关注（或忽略）」落地，用确定性打分 + 分级分析控制噪声与成本。这是三份计划书反复验证后的唯一收敛结论。
