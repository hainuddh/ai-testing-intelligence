## 1. 系统简介

AI Testing Intelligence 是一套 AI 智能测试情报系统，围绕以下工作流运行：

- **发现**：按平台关注方向自动寻找来源并独立试运行，用户确认后持续采集 RSS / Atom / 网页内容；同时按GitHub关注主题自动探索项目；
- **分析**：由 AI 模型评估内容的测试相关性、测试价值，生成摘要、适用场景、落地建议与风险；
- **去重**：RSS/Atom与人工录入按原文URL或标准化标题去重；GitHub推荐排除所有已进入历史报告的项目；
- **交付**：内容情报卡片与GitHub研究日报在站内展示，支持Markdown导出，合格新结果可进入每日邮件。

系统通过浏览器访问管理界面，具体访问地址由系统管理员提供。首次使用前，请确认已获得有效账号；为获得完整的页面和下载功能，建议使用近期版本的主流浏览器。

## 2. 角色与权限

系统内置三种角色，权限由低到高：

| 角色 | 权限 |
| --- | --- |
| 浏览者（viewer） | 查看和筛选内容情报、详情及Markdown导出；查看GitHub研究、历史报告和探索状态；查看信源、贡献、试运行样例及采集端点 |
| 维护者（maintainer） | 在浏览者基础上，可管理平台关注方向、确认试运行来源启用、新增和编辑信源、暂停恢复归档，管理采集端点，为微信/微博信源人工录入内容；管理GitHub关注主题和候选反馈 |
| 管理员（admin） | 在维护者基础上，可删除信源、管理采集内容、管理用户、查看数据库状态，配置每日邮件和收件邮箱、查看发送记录及重试 |

所有角色都能看到「内容情报」「GitHub 追踪」「信源管理」。维护者可以在这些页面进行相应维护操作；管理员还可进入「采集管理」「用户管理」「数据库状态」「邮件推送」。

## 3. 登录与退出

1. 在浏览器打开系统地址，进入登录页。
2. 输入管理员分配的用户名和密码，点击「进入雷达」。
3. 登录成功后进入仪表盘；用户名和角色显示在右上角。

> 提示：登录状态保存在当前浏览器本地，请勿在公共设备上保留登录状态。会话失效后系统会自动登出，重新登录即可。右上角的退出按钮可随时手动退出。

## 4. 内容情报

「内容情报」展示已完成分析、达到系统测试相关性门槛，并满足当前最低价值分条件的情报卡片，是日常浏览的核心页面。默认每页显示 12 条，并优先显示测试价值分较高的内容。

### 4.1 检索与筛选

工具栏提供以下筛选条件：

- **关键词检索**：检索标题、摘要或正文，回车或点击「检索」生效；
- **开始/结束日期**：优先按内容发布时间筛选；没有发布时间时，使用采集时间。结束日期不得早于开始日期；
- **情报分层**：「主雷达」展示相关性和价值均达到推荐门槛且具备可执行建议的内容；「观察池」保留达到观察门槛、但尚未满足主雷达条件的内容；
- **最低价值**：选择「观察 40+」「推荐 60+（默认）」或「高价值 80+」。该条件仅调整测试价值分门槛，不会绕过系统配置的测试相关性门槛；
- 「应用筛选」确认条件，「重置」恢复默认（主雷达、清空关键词和日期、价值分回到 60）。

筛选或翻页时页面会短暂显示加载状态。若刚完成采集或分析但列表未更新，可等待片刻后重新进入该页面或再次应用筛选。

### 4.2 查看情报详情

点击卡片标题或「查看测试情报」，弹出详情窗口，包含：

- 情报摘要；
- 测试价值分析；
- 适用测试场景、落地验证建议；
- 风险与边界；
- 高价值内容原文中提炼出的相关工具、研究、会议或参考资料链接；
- 标签、相关性分与价值分；
- 「查看原文」跳转到外部原文链接（在浏览器新标签页打开）。

### 4.3 导出 Markdown 报告

1. 勾选要导出的情报卡片（支持跨页选择，单次最多 100 条）；可用「全选当前页」或「清空选择」快速操作；应用新的筛选条件或重置筛选会清空当前选择；
2. 点击「导出 Markdown (N)」；
3. 浏览器自动下载合并的 Markdown 报告文件。

报告按选择顺序输出，包含每条情报的评分、测试价值分析、适用场景、落地建议、风险、标签、相关链接和原文证据链接，可直接用于测试评审或归档。若浏览器阻止自动下载，请允许当前站点下载文件后重试。

测试价值达到 60 分的内容完成分析后，后台会分批受限读取一次原文页面，从原文实际存在的链接中最多提炼 5 条相关资料。链接由程序确定性提取，不要求模型生成 URL，也不会继续抓取链接指向的页面；未找到合适链接时不显示该区域。外部链接内容不受本系统控制，访问前仍应核对域名和来源。

## 5. 信源管理

「信源管理」提供信源列表、发现与试运行、需处理和已归档视图，支持搜索筛选及分页。顶部展示全部、监听、暂停和需处理数量；来源卡片展示近30天已分析、入选、待分析及采集健康。点击「管理关注方向」后，平台自动探索来源，由用户查看实际样例并确认正式启用。完整流程见[信源工作台](source-management-zh.md)。

### 5.1 新增信源（维护者/管理员）

推荐通过「通过网址添加」直接验证并建立订阅；「手动新增信源」用于先保存来源资料，填写：

| 字段 | 说明 |
| --- | --- |
| 信源名称 | 必填，全局唯一 |
| 信源类型 | 网站 / 通讯 / RSS / 社交媒体 / 微信公众号 / 微博 |
| 可信等级 | 1-5：5 最高可信、4 高可信、3 待验证、2 观察中、1 低可信 |
| 主页地址 | 可选，需为有效 URL |
| 描述 | 可选，信源说明 |
| 语言 | 必填，从列表中多选所需语言 |
| 关注主题 | 至少一个；在独立输入框中逐项添加，如先添加 `AI Agent`，再添加 `foundation-models`，详见5.6节 |

点击「建立监听」保存。新建信源后，还需按 5.4 节添加采集端点，系统才能自动采集内容；微信公众号和微博也可按 5.5 节人工录入。信源名称重复时系统会提示冲突。

RSS / Atom 端点如果误填为栏目网页、发生跳转或原地址失效，系统会从当前响应或信源主页读取网站声明的订阅地址，并在当前站点内有限探测常见订阅路径。候选地址必须验证为有效订阅格式才会自动修正端点；有效但暂时为空的订阅不视为故障。无法确认时保留原配置并将端点标记为异常，不会调用搜索引擎或无限尝试。对于缺少摘要的少量新条目，系统会受限读取文章页的描述信息作为补充。

### 5.2 通过网址添加（维护者/管理员）

点击「通过网址添加」，输入网站主页后选择「开始探测」。平台会读取网站声明的 RSS / Atom 地址，并在当前站点内有限验证常见订阅路径。发现成功后会展示已验证订阅和最近文章样例。按关注方向自动寻找新站点在「发现与试运行」中执行，无需每天手动探测。

确认样例符合预期后，填写信源名称、语言、可信等级，按需添加关注主题，点击「确认并启用监听」。自动发现确认允许主题暂时为空，后续普通编辑时需补充至少一个主题。服务端会再次验证订阅地址，并一次性创建已启用的网站信源和健康的 RSS / Atom 端点；端点默认每 360 分钟采集一次、单次最多 50 条。验证失败或名称冲突时不会留下半成品信源。浏览者没有发现或创建权限。

### 5.3 编辑与删除信源

- **编辑**（维护者/管理员）：点击卡片「编辑」修改字段后保存；
- **暂停、恢复、归档**：保留历史内容，停止或恢复新采集；归档记录可在「已归档」恢复。
- **永久删除**（仅管理员）：在「查看贡献」的高级操作中确认。删除会级联清除该信源的全部采集内容且无法恢复，日常停用应使用暂停或归档。

### 5.4 管理采集端点

点击卡片「采集端点」打开端点抽屉。所有角色可查看，维护者和管理员可新增、编辑、启停或删除端点。日常调整地址或间隔直接编辑，暂时停用使用开关，保留运行历史。

新增端点时填写：

| 字段 | 说明 |
| --- | --- |
| 端点名称 | 必填，如「官方 RSS」 |
| 采集类型 | RSS / Atom 或网页；微信公众号、微博仅允许 RSS / Atom |
| 采集间隔（分钟） | 15 - 10080，默认 360；表示两次计划采集的最短间隔 |
| 采集地址 | 必填，需为有效 URL；生产环境建议使用 HTTPS |
| 单次最大条数 | 1 - 500，默认 50；仅表示一次处理的条目上限 |

点击「添加采集端点」保存。新端点由后台采集任务按轮询周期异步处理，不保证保存后立即出现内容。

端点列表会显示健康状态：`unknown` 表示尚未完成采集，`healthy` 表示最近一次采集成功，`unhealthy` 表示最近一次采集失败。信源卡片汇总为「等待首次采集」「采集正常」「部分异常」或「采集异常」，并显示最近成功时间及最近错误。RSS / Atom 端点异常时，平台会先按上述规则自动发现并验证替代地址；仍未恢复时，再检查地址可访问性、内容格式和 Worker 日志。

删除端点时点击端点右上角删除按钮并确认。删除后，该端点的配置和采集运行历史无法恢复，但已采集内容仍保留；如需删除内容，由管理员在「采集管理」中操作。

### 5.5 人工录入内容（微信/微博，维护者/管理员）

微信公众号、微博信源卡片上会出现「录入内容」按钮。系统不会抓取平台页面，而是使用你填写的信息进入去重与情报分析流程。填写：

- 内容标题（必填，最多 500 个字符）；
- 原文地址（必填，有效 URL）；
- 内容摘要（必填，最多 20000 个字符，建议包含关键事实与测试价值线索）；
- 发布日期（可选）。

点击「提交分析」后，内容进入异步分析队列，不会立即出现在「内容情报」。管理员可在「采集管理」中查看处理状态和分层原因；分析后可能进入主雷达、观察池或已过滤层。相同原文地址或标题只能录入一次，重复提交会提示内容已存在。请确保内容来源合法并保留原文证据链接。

### 5.6 管理关注主题

信源新增、编辑和自动发现确认共用逐行主题编辑器，GitHub关注主题也采用相同操作方式。

1. 在「新增关注主题」中输入一个方向，点击「添加主题」或按回车。支持 `AI testing` 这样的含空格词组，每次只添加一个主题。
2. 修改已有主题时，点击该行「编辑」，填写后点击「确认修改」；也可以「取消编辑」。空主题或重复主题会提示错误。
3. 在主题的「更多操作」中选择「移除主题」，该行保留并标记「待移除」；保存前点击「撤销」即可恢复。
4. 核对底部「新增 N · 修改 N · 移除 N」，再点击抽屉底部保存按钮。正在输入但尚未添加、或行内修改尚未确认时，需先处理该项才能保存。

新增或修改主题在保存成功后生效；输入框里的回车只确认当前主题操作，不会直接提交整个信源。取消关闭后放弃草稿，重新打开显示已保存配置；保存失败保留草稿供重试。普通新增/编辑信源至少保留一个主题，全部标记移除后需撤销或补充主题才能保存。

信源主题用于管理该信源的方向，不自动改写采集端点或同步到GitHub关注主题。GitHub主题用于平台下一轮项目搜索，两处配置分别维护。

### 5.7 平台关注方向与试运行

1. 维护者或管理员点击「管理关注方向」，填写想持续了解的方向，选择语言、排除项和同时试运行上限后保存。该配置为平台共享；关闭探索或清空方向不会停止已有正式信源。
2. Worker默认每天从维护的信源目录和已分析文章中的真实引用站点探索来源。首版不覆盖全网，目录主要是英文技术来源；无需用户每天手动启动。
3. 在「发现与试运行」查看发现依据、已验证订阅和实际文章样例。默认同时试运行3个来源，可设1—5个；每轮每源最多处理5篇样例，累计最多20篇。未配置模型或调用失败时显示待处理，不以零分代替分析。
4. 至少5篇样例完成分析后显示「可评估」，这是样本条件，不是质量担保。查看实际贡献后点击「确认正式启用」，二次确认后才建立正式信源；平台不会自动转正。
5. 暂不决定可暂停候选；不适合的候选可以忽略，平台保留决定并停止反复推荐。通过「查看已忽略」可找回并恢复，恢复仍受试运行上限约束。

试运行样例不进入主雷达和每日邮件，也不成为邮件必须等待的任务。正式启用后按正常规则采集和分析；平台不会直接把试运行样例加入邮件。

正式来源的「查看贡献」展示近30天保留内容的统计和最近样例。待分析数量与已分析数量分列；跨源去重后的归属受采集先后影响，不能把这些统计当作准确原创率或独家贡献。暂停、归档均保留历史，恢复后按正常周期继续，不重新打开已跳过的当日邮件采集任务。

## 6. 采集管理（管理员）

「采集管理」展示自动采集和人工录入的全部内容。分析状态与展示分层分开记录：状态表示任务是否完成，分层表示内容进入主雷达、观察池还是被过滤。默认每页显示 20 条，按采集时间倒序排列。

状态含义如下：

| 状态 | 含义 |
| --- | --- |
| 待分析 | 内容已经入库，等待后台分析任务处理 |
| 分析完成 | 模型已生成评分与分析结果；具体展示位置由分层决定 |
| 分析失败 | 模型调用或结果处理失败；后台会按计划自动重试 |

分层含义如下：

| 分层 | 含义 |
| --- | --- |
| 主雷达 | 相关性、测试价值和可执行建议均达到推荐门槛 |
| 观察池 | 达到观察门槛，但相关性、价值或建议完整度尚未达到主雷达要求 |
| 已过滤 | 模型判定不相关，或相关性/价值低于观察门槛 |

列表和详情会显示具体分层原因。管理员可勾选最多 100 条内容，点击「重新分析」将旧评分和结论清空并重新加入分析队列，适用于规则、模型或内容策略升级后的历史数据复核。

### 6.1 查询与筛选

- **关键词查询**：查询标题或摘要；
- **分析状态**：待分析 / 分析完成 / 分析失败；
- **内容分层**：主雷达 / 观察池 / 已过滤；
- **信源**：按信源过滤；
- **开始/结束日期**：按采集时间过滤。

设置条件后点击「应用筛选」；需要清除条件时点击「重置」。

### 6.2 查看采集详情

点击内容标题可查看原始摘要、信源、分析状态、相关性与价值评分、分析次数、发布时间、采集时间和分析时间。高价值内容若已从原文提炼出相关资料，也会显示「相关链接」。分析失败的内容还会展示完整失败原因；点击「查看原文」可在新窗口打开外部原文地址。

### 6.3 删除采集内容

- **单条删除**：点击某行右侧删除按钮并确认；
- **批量删除**：勾选多条（单次最多 100 条）后点击「批量删除 (N)」并确认。

删除某条采集内容会同时删除其分析结果，并从「内容情报」移除，但不会删除信源或采集端点。列表可能需要短暂刷新才能反映变化。删除操作不可撤销；批量删除中只要包含不存在的记录，本次批量操作就不会执行。

> 说明：分析失败的行会以红色状态显示，悬停可见失败原因，便于排查采集或分析配置问题。

## 7. 用户管理（管理员）

「用户管理」列出所有账号，支持新增、编辑、停用/启用和删除。

### 7.1 新增用户

点击「新增用户」，填写：

- 用户名（必填、唯一，最多 100 个字符）；
- 初始密码（8 - 200 个字符）；
- 角色：浏览者 / 维护者 / 管理员；
- 账号状态：启用 / 停用。

点击「创建用户」保存。用户名重复时系统会提示冲突。

系统当前不提供用户自助修改密码功能。用户忘记密码时，应联系管理员通过「编辑用户」设置新密码；管理员应通过安全渠道告知新密码。

### 7.2 编辑用户

点击「编辑」可修改用户名、角色、账号状态，或设置新密码（留空则不修改）。停用后的用户将无法继续通过系统鉴权。系统有以下保护规则：

- 不能停用自己的账号；
- 不能移除系统最后一个启用的管理员；
- 不能把必要字段清空。

### 7.3 删除用户

点击「删除」并确认。以下情况无法删除：

- 当前登录用户自己（删除按钮对本人置灰）；
- 最后一个启用的管理员；
- 拥有信源的用户。当前 Web 界面不支持转移信源所有权，需先由管理员删除该用户拥有的信源，再删除用户。

## 8. 数据库状态（管理员）

「数据库状态」显示当前存储引擎（dialect）与核心数据表行数：

- 用户；
- 信源；
- 采集端点；
- 内容条目；
- 采集运行。

该页面仅用于快速了解数据资产规模，不提供修改能力。页面数据可能存在短时间缓存，刚完成新增或删除后可稍候再重新进入页面查看。

## 9. GitHub追踪

导航「GitHub 追踪」进入项目研究页。平台主动发现、筛选和研究项目，用户不必每天手动新增候选、点击发现或先关注项目。

### 9.1 查看研究与探索状态

页面先显示自动探索状态、最近/下次探索时间和关注方向，再显示最新研究。报告包含项目摘要、测试价值分析、应用场景和落地建议，可直接「下载 Markdown」。展开「历史报告」，点击「查看」可阅读并下载以往日报。

每个业务日期最多推荐5个新项目；全新指平台从未在报告中推荐过，不等于仓库刚刚创建。曾进入任何历史报告的项目会被排除，历史报告仍可回看。仅被搜索到、关注或分析过但尚未进入报告的项目仍有机会推荐。没有新项目时允许本轮无报告，不使用旧项目凑数。

「刷新结果」只重新读取当前结果。探索运行中可稍后刷新，失败时查看下次探索时间，平台会按退避与限流等待自动重试。未启用邮件或没有启用邮箱时，正常探索成功后按24小时安排下一轮；启用邮件且有收件人时，探索对齐每日邮件准备时间。

### 9.2 设置主题与候选反馈（维护者/管理员）

点击「关注主题」，按5.6节逐项新增、编辑或标记移除，核对变更数量后点击「保存关注主题」。保存后的主题用于后续探索；全部清空后回到默认语言范围搜索，不会关闭探索。浏览区域的主题只用于展示，不能点击标签直接删除。

展开「候选管理」可按状态和主题筛选，查看项目、语言、Stars、动量及状态，并选择「关注」或「忽略」。默认列表不含已忽略项目，查看它们需切换到「已忽略」；可重新关注来恢复参与筛选。关注是可选反馈，不保证入选，也不是研究的前置条件。已进入报告的项目自动移出候选；再次关注不会解除历史排除规则。

当前提供日报和Markdown，不提供GitHub周报/月报或已研究项目的持续趋势报告。

## 10. 邮件推送（管理员）

### 10.1 启用与收件邮箱管理

1. 进入「邮件推送」，确认发件服务已由管理员配置。若显示未配置提示，按[每日情报邮件说明](daily-email-digest-zh.md)配置后台SMTP。
2. 点击「新增收件邮箱」，填写邮箱、名称或备注，并启用。至少有一个启用邮箱后，才能打开总开关。
3. 设置内容情报价值门槛和每日发送时间，打开「启用每日邮件」，点击「保存邮件设置」。时间按北京时间计算，页面同时显示对应准备和截稿时间。
4. 在「每日准备进度」查看任务，在「发送记录」查看各邮箱的结果；两处分别提供刷新按钮。

收件邮箱支持搜索、编辑、暂停/恢复及删除，点击邮箱行「查看记录」可筛选该邮箱。总开关和邮箱开关均开启时才投递。暂停后恢复同一邮箱保留原接收窗口，修改邮箱地址会重新建立窗口；删除邮箱保留历史发送与去重记录。

### 10.2 什么会进入邮件

邮件合并主雷达高价值内容和已发布的GitHub研究日报。内容价值分须严格超过配置门槛，默认70对应71分及以上；GitHub项目不再次套用这项门槛。内容按分析完成时间、GitHub日报按生成时间判断是否晚于邮箱开始接收时间，并受本批范围及每个邮箱的去重记录约束。新邮箱不自动补发启用前的历史结果。

每封邮件合计最多100条，正文包含摘要、评分、建议和链接，完整报告作为Markdown附件。任一类有符合条件的新内容就发送，两类都为空则记录「无新内容」，情报数为0，不发送空邮件。

### 10.3 发送时间与修改规则

平台提前2小时建立批次并补齐采集和研究，发送前10分钟截稿。例如配置17:00，则15:00准备、16:50截稿、17:00计划投递；配置01:00则在前一天23:00准备。截稿前开始的本批任务晚完成仍计入当天；本批未完成时延迟发送，截稿后的普通新内容结转下一天。

**时间修改对之后新建的批次生效，已建立批次保留原安排。** 当天尚未建立批次时可使用新设置；如果已建立，不会因为修改时间另建同日邮件。以「每日准备进度」中的实际计划时间为准，而不是仅看设置输入框。凌晨发送的次日批次可能已在前一晚建立。

例如今天已经存在06:30开始、08:20截稿、08:30计划发送的批次，下午改成17:00，今天仍按08:30这批处理；下一批尚未建立时，明天才按17:00安排。今天如果已因0条内容跳过，也不会在17:00重开。调整每日时间不能用来立即测试发信，当前没有独立的测试邮件按钮。

### 10.4 查看结果与重试

| 页面或状态 | 说明与下一步 |
| --- | --- |
| 准备中 / 延迟准备 | 等待截稿或本批任务完成；到计划发送时间仍未完成时显示延迟准备，查看各项进度和原因 |
| 准备完成 | 前置任务完成，还需查看各邮箱发送记录；不代表已发送 |
| 无新内容 | 本邮箱本批筛选后0条，跳过邮件；不是SMTP投递失败 |
| 等待发送 | 已排队，核对该记录的计划时间；过期仍未发送时联系管理员检查独立投递服务及配置 |
| 发送中 | 正在向发件服务投递 |
| 已发送 | 发件服务已接受；未收到时再查收件箱、垃圾邮件及服务商投递情况 |
| 发送失败 | 查看错误、尝试次数和下次尝试时间；每轮最多尝试3次，达到上限后可点击「重试」 |
| 待确认 | 无法确认是否已被发件服务接收，不自动重发；先核对收件箱，再决定是否手动重试 |

“采集7/7、分析24/24、GitHub研究已完成”是准备进度，不是可发送数量。内容可能进入观察池、未超过邮件门槛、早于邮箱启用时间，或已被此邮箱的投递记录收录；GitHub研究完成也可能没有新项目。因此准备完成与0条邮件可以同时出现。

没有今天的发送记录时，检查邮箱是否在今天截稿后才开始接收，以及总开关和邮箱是否启用。仅修改时间不会补发旧批次。更多原因及管理员检查命令见[邮件排查说明](daily-email-digest-zh.md)。

## 11. 常见问题

**Q：为什么「内容情报」里什么都没有？**
未配置 AI 分析模型时，采集的文章会停留在待分析状态，情报流保持为空，避免把未经评审的普通 AI 新闻混入。请管理员按部署手册配置 OpenAI 兼容的分析模型。

**Q：为什么有些已采集的内容没有出现在「内容情报」？**
内容可能仍在等待分析、分析失败、进入观察池或已过滤，或者测试价值分低于当前页面筛选值。管理员可在「采集管理」中查看状态、分层、评分和具体原因，并在策略升级后选择重新分析。

**Q：重复内容会被重复采集吗？**
RSS / Atom 内容和人工录入内容按原文 URL 哈希或标准化标题去重，重复 URL、转载链接或同标题内容会被跳过或拒绝。网页类型端点会定期更新同一 URL 的内容并重新进入分析，而不是创建重复记录。

**Q：微信/微博为什么不能配置网页类型端点？**
平台页面存在访问与版权边界，系统仅接受来源明确、已获授权的 RSS / Atom 地址；平台内容通过「录入内容」人工提交，且不会自动抓取页面。

**Q：导出的报告为什么有条数限制？**
单次报告最多选择 100 条情报，超出部分需分批导出。

**Q：登录时提示「登录状态已失效」？**
登录令牌过期或会话失效，重新登录即可。

**Q：端点显示 `unhealthy` 怎么处理？**
系统会先尝试从当前响应或信源主页发现新的 RSS / Atom 地址，并有限验证同站常见订阅路径；成功后会自动更新端点。可在信源卡片或「需处理」查看最近错误。若后续采集仍显示 `unhealthy`，再确认目标站点能从服务器访问、没有拒绝请求，并联系管理员结合 Worker 日志进一步排查。

**Q：页面提示网络异常或请求失败怎么办？**
先刷新页面并重试；若持续出现，记录当前页面、操作步骤和提示文字，联系管理员检查 API、Worker、数据库和网络状态。不要反复提交新增或删除操作，以免造成重复请求。
