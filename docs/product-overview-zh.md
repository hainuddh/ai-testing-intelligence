# SIGNAL ATLAS · 技术情报雷达产品说明

更新日期：2026-10-18。本文描述当前仓库已实现的产品能力；线上可用功能还取决于部署版本、模型配置及后台服务状态。

## 1. 产品定位

AI Testing Intelligence（SIGNAL ATLAS）面向测试团队、技术研究人员和平台维护者，将技术文章与开源项目转化为可评估、可验证的测试情报。用户可以查看测试价值、应用场景、落地建议和原始证据，在站内阅读、导出Markdown，或由管理员配置每日邮件。

平台有两条发现路径：信源按用户定义的方向自动探索，经过独立试运行和用户确认后进入正式监听；GitHub项目由平台按关注方向主动探索、研究并发布日报。两条路径都不要求用户每天手动发起候选。用户可依据实际内容贡献和运行状态调整正式信源。

## 3. 内容情报流程

```text
定义关注方向 → 平台自动发现 → 独立试运行 → 用户确认正式启用
通过网址添加或手动配置 ──────────────────→ 正式信源
正式信源 → RSS、Atom、网页采集或人工录入 → 历史去重
         → 模型分析 → 主雷达 / 观察池 / 已过滤
         → 站内阅读与Markdown导出 → 符合邮件规则的内容进入每日汇总
```

试运行默认同时观察3个来源，每个来源累计最多20篇独立样例；至少5篇完成真实分析后标记为可评估，不自动转正。未配置模型或分析失败时保留待处理状态。样例不进入正式内容、雷达或邮件，确认正式启用后才开始常规采集。

RSS/Atom与人工录入按原文URL或标准化标题去重。网页端点内容变化后更新同一URL并重新分析；未变化时保留已有分析。微信/微博使用来源明确的RSS/Atom或人工录入，不提供原生平台页面自动抓取。

正式信源提供近30天贡献、样例和采集健康信息。暂停、归档和恢复保留历史及端点配置；端点地址、周期、上限和启停可直接调整。统计基于当前保留的归属内容，不等于准确原创率、独家贡献或重复率，不按短期产量自动淘汰来源。

分析输出包括相关性与价值评分、摘要、测试价值分析、适用场景、落地建议、风险及标签。任务的“分析完成”表示处理结束，内容可能进入观察池或已过滤。未配置模型时，文章保留为待分析，不直接进入情报流。

主雷达浏览默认最低价值分为60，用户可调整浏览筛选。邮件使用单独配置的价值门槛：默认严格大于70，即71分及以上；调整浏览筛选不会改变邮件门槛。内容情报单次合并导出最多100条，按勾选顺序生成报告。

## 4. GitHub主动探索与研究

平台从关注主题搜索相关仓库，进行确定性评分和模型研究，自动发表日报，每个业务日期最多推荐5个新项目。这里的“新”指平台从未在报告中推荐过，不要求仓库刚创建。

只要项目进入过任意历史报告，就从后续新推荐中排除，包括旧报告里分析不完整的条目。仅搜索到、关注过、分析过但未入报告的项目仍可后续研究；忽略或归档的项目不参与自动推荐。历史报告继续保留供查看和下载。

未启用邮件或没有启用收件人时，探索成功后通常按24小时安排下一轮；启用邮件且有有效收件人时，探索与每日邮件准备时间对齐。失败遵守重试和GitHub限流等待，页面展示最近及下次探索时间。没有符合条件的新项目时，探索状态提示本轮暂无新项目，不生成空报告；页面仍保留已有的最新研究供查看，不用旧项目补足新报告数量。

页面以最新研究为主，历史报告和候选管理可以展开查看。“刷新结果”重新读取当前结果，不会启动新一轮研究。关注项目属于可选反馈，不是获得研究报告的必要操作。

## 5. 关注主题的管理方式

信源新增、编辑、自动发现确认以及GitHub关注主题使用相同的逐行管理方式：每次添加一个主题，支持含空格的词组；已有主题可编辑，通过更多操作标记移除，保存前可以撤销。底部显示新增、修改、移除数量，保存成功后才生效，取消关闭会放弃草稿，保存失败保留草稿。

| 主题所在位置 | 用途与规则 |
| --- | --- |
| 单个信源 | 描述和管理该信源的关注方向，并作为模型分析的信源上下文；不直接替代端点采集规则，也不与GitHub主题自动同步。普通新增/编辑至少保留一个主题；自动发现确认允许暂不填写 |
| 信源工作台的关注方向 | 平台探索新来源的方向，支持语言和排除项；清空时不探索，正式监听不受影响。试运行后由用户确认启用 |
| GitHub追踪 | 平台统一的探索方向；保存后用于后续探索。清空后回到默认语言范围发现，不代表关闭探索 |

输入尚未添加或行内修改尚未确认时，需要先完成或取消该项操作再保存。主题不再通过标签上的关闭按钮直接删除。

## 6. 每日邮件的内容与时间规则

### 6.1 收到哪些内容

一封邮件可同时包含内容情报和GitHub研究，任一类有合格的新结果就可发送。内容情报须通过主雷达准入并严格超过邮件价值门槛；GitHub部分使用已发布日报的研究结果，不再次套用内容情报的邮件门槛。

每个邮箱从开始接收的时刻建立自己的窗口：内容按分析完成时间、GitHub日报按生成时间判断，不自动补发此前的历史内容。暂停后恢复同一邮箱保留窗口；修改邮箱地址重新建立窗口。内容按原文、GitHub项目按仓库名称分别记录每个邮箱的去重凭据，已排队或已发送的条目不会被后续邮件重复选取。

每封两类内容合计最多100条。两类都有积压时为GitHub研究保留最多50条名额，其余用于内容情报；邮件条数与当天GitHub新推荐最多5个属于不同范围。超出邮件上限的未发送结果可结转后续批次。

### 6.2 准备、截稿与投递

所有计划时间按北京时间计算。

| 配置发送时间 | 开始准备 | 截稿 | 计划投递 |
| --- | --- | --- | --- |
| 09:00（默认） | 当天07:00 | 当天08:50 | 当天09:00 |
| 17:00 | 当天15:00 | 当天16:50 | 当天17:00 |
| 01:00 | 前一天23:00 | 当天00:50 | 当天01:00 |

平台持续采集，在准备阶段建立当天批次并补齐任务。截稿关闭普通新内容的输入边界；截稿前已开始的本批任务即使晚完成，仍归入当天。截稿后的普通新内容留待下一天。

本批采集、分析、GitHub研究都完成并到达截稿时间后，才冻结各邮箱的邮件。暂停、归档信源或停用端点时，未执行的采集义务记为跳过并保留原因，已开始的请求允许收尾；独立试运行不属于邮件前置任务。已冻结的邮件保持原快照。

独立投递服务在计划时间到达后处理队列；如果本批任务尚未完成，则显示延迟原因，完成后再补发。计划时间不是保证收件箱到账的时间。新生成邮件主题为“每日测试情报 · 日期 · N条”。

### 6.3 修改时间何时生效

**已建立的批次保留原准备、截稿和发送安排；时间修改对之后新建的批次生效。** 如果当天尚未建立批次，后续创建时使用已保存的新设置。凌晨发送的次日批次可能在前一天已经建立，不能简单理解为所有修改都从明天生效。

例如10月11日已建立06:30准备、08:20截稿、08:30发送的批次，下午把设置改为17:00，当天仍按原批次处理，不会额外创建17:00的邮件。若下一批尚未建立，10月12日按15:00准备、16:50截稿、17:00计划投递。

同一邮箱每个日报日期只建立一份投递记录。当天记录已经“无新内容”结束，也不会因修改时间或下午出现新内容而重新打开。当前没有独立的“发送测试邮件”或“立即补发今天”入口。

### 6.4 如何判断邮件结果

“每日准备进度”描述任务，“发送记录”描述各邮箱的结果；应结合查看。

| 页面状态 | 含义与处理 |
| --- | --- |
| 准备中 / 延迟准备 | 等待截稿，或本批任务仍在运行/重试；到计划发送时间仍未完成则为延迟准备，查看进度和原因 |
| 准备完成 | 本批前置任务已完成；继续看各邮箱发送记录确认结果 |
| 无新内容，情报数0 | 两类内容经筛选和去重后均为空，跳过空邮件 |
| 等待发送 | 邮件已排队；核对记录中的计划时间，逾期则排查投递服务和配置 |
| 发送中 | 正在尝试交给发件服务 |
| 已发送 | 发件服务已接受，最终收件还受邮箱服务影响 |
| 发送失败 | 明确连接、认证或投递失败；每轮最多尝试3次，耗尽后可由管理员重试 |
| 待确认 | 无法确认发件服务是否已接收；先核对收件箱再决定重试，系统不自动重发 |

采集7/7、分析24/24、GitHub研究已完成，只说明任务完成。24条内容可能不满足主雷达/邮件门槛、早于邮箱启用时间或已投递；GitHub研究完成也可能没有新项目。最终情报数可以是0。完整筛选、重试与排查说明见[每日情报邮件说明](daily-email-digest-zh.md)。

## 7. 使用前提与当前边界

管理员需要配置分析模型、数据库和后台服务；完整部署由API、Worker、独立mail-sender及前端共同工作。SMTP参数通过部署环境配置，管理员在页面维护收件邮箱、总开关、门槛与时间。仅部署静态前端不能执行自动采集、研究和发信。

当前提供GitHub日报、站内展示、Markdown导出和每日汇总邮件。GitHub周报/月报、已研究项目持续快照趋势分析、IM推送、前端PAT配置及用户个人订阅中心尚未提供。评分与建议用于辅助技术判断，落地前仍需结合团队场景验证。
